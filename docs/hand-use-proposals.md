# Nonbutton hand-use proposals

`HIGGS_QueryHandUseProposalsInterface` version1 adds a collection round for contact, dwell, posture and game-activation consumers. It complements the existing immediate HandUse and button-candidate APIs without changing their public layouts. A mod proposes one of the fixed hand-use kinds, the entire desired physical-hand mask, a live executor and its own context identity. It does not invent a controller press or a custom hand state.

`Propose` copies the request and returns a proposal ID. Pending proposals have no grant, do not reserve a hand and cannot authorize a mutation. The request includes current hand generations and a collection deadline of1–1000ms. It is one-shot: its eligibility is rechecked at the next HIGGS main maintenance, rather than automatically retrying until the hand becomes free. At most eight pending proposals per client are retained, with one per kind/context ID/context generation.

At that maintenance boundary HIGGS freezes the pending set and sorts by effective user priority, then client registration order, then proposal order. The existing `hand-broker.ini` priority map applies here too, including changes made before selection. It accepts a disjoint set of proposals atomically. A request for both hands receives both or neither; rejection does not reserve a spare hand that a later disjoint proposal could use. Existing physical use and grants are never preempted. This is a deterministic greedy priority policy, not maximum-cardinality scheduling or starvation prevention.

Each accepted proposal becomes an ordinary HandUse session with the same request ID, a new grant and `inputId=0`. Its requested session duration starts at acceptance, not submission. Existing Renew/End, footprint Resize, granted physical operations and confirmed-result reporting apply. The assigned executor receives one main-maintenance notification. Reentrant submissions and recursive drain calls cannot join the closed round; they wait for later maintenance. All decisions in the closed set are made before invoking an executor.

`Copy` returns pending/accepted/rejected/cancelled, the round ID, effective priority and the ordinary copied HandUse state after acceptance. The admission decision remains accepted if that session later ends; `use.active` and ordinary action results describe its subsequent lifetime. The shared bounded broker history can evict old terminal records. `Cancel` cancels pending work only; after acceptance use EndHandUse so ordinary dependent cleanup remains authoritative.

UI entry, world/load change, expiry, invalid current hand generations, executor/client removal, explicit cancellation and changed eligibility prevent a stale proposal from starting. Even opening and closing a menu between maintenance calls invalidates the pending proposal. A late legacy immediate HandUse request cannot jump an overlapping already collected proposal. An already acquired immediate session, a separate controller priority round or native physical possession remains an existing use; this table does not promise one global scheduler across frames or input mechanisms.

Climbing and harvesting can submit their competing nonbutton opportunities to this shared round and reuse the resulting session/footprint transitions instead of privately disabling one another. Their surface rules, pulling thresholds, loot and locomotion remain domain work. A consumer must actually adopt this API; registering a proposal does not port an existing mod.

Run `python tests/run_hand_tests.py --build-dir <external-directory>`. Production authority cases exercise submission-order independence, user overrides, ties, atomic/disjoint selection, absent pending authority, once-only notifications, cancellation, menu/load/generation/executor/client invalidation, bounded capacity and callback reentry. The C layout consumer and isolated DLL probe negotiate this separate table. Full native compilation is additional evidence; neither fixture nor compilation qualifies Skyrim behavior or hardware input.
