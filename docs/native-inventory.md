# Native player inventory transactions

The separate [InventoryInterface](../include/higgsinventory.h) supplies the common native executor for ordinary player inventory operations. A consumer selects an actual observed stack and uses the existing [TransactionsInterface](../include/higgstransactions.h); it does not need its own drop, pickup or hand-equipment implementation. Official001 and the existing transaction table remain unchanged. This is implemented source, compiled into the native DLL and exercised through explicit engine doubles; running Skyrim behavior and consumption effects have not been qualified.

## Selection and ownership

`RequestSelection(client, request)` queues a player-inventory selection. It reads no engine object on the calling thread. The existing HIGGS main maintenance pump resolves the base form, current container changes and current extra lists, retains the actual player reference and mints a `HIGGS_ITEM_NATIVE_INVENTORY` identity through the private transaction owner. `CopySelection` returns Queued, Ready or Invalid with the reason. Ready is selection evidence, not a transfer commitment.

`stackOrdinal=0` selects the unextended homogeneous stack. Ordinals 1..N select the extended lists in that observed inventory entry order. The resulting ticket binds that actual observed stack; it never reuses the ordinal to select a replacement later. A requested quantity must fit the selected stack. A consumer that needs to choose between custom enchanted instances still needs its inventory selection UI/data source; this service supplies a safe native ticket, not an inventory browser.

The native locator keeps a retained container, base form, copied existing unique ID when available, integer list identity, stack count, total count and engine-event version. Every mutation resolves the live inventory entry and list again. A saved integer address is only compared with fresh live list addresses, never dereferenced. Existing UIDs allow a freshly relocated list to be found without using its old address. A conservative global inventory/UID event version invalidates selections after any observed inventory/UID event, including unrelated changes. No UID is manufactured and selection performs no engine metadata mutation.

`GetExecutor(client)` returns one HIGGS-owned transfer executor registered to that same client. Put its token and the Ready native identity into the normal transfer request, preserving the consumer's grant and idempotency key. Held-to-inventory and consume requests use `CopyHeldItem` and the same native executor. They resolve the retained actual native reference from the hand owner, rather than looking up a possibly recycled form ID. The ABI exposes no engine pointer.

Ticket release cannot discard an active or recovery-required transaction's item lock. Released ticket identities are retired at the main pump only after the transaction owner permits it. Current native held identities are likewise retained while held or used by any live/recovery transaction, and retired by the actual native reference-erasure path after that authority ends. Private monotonic instance IDs are not recycled when bounded item slots are reused.

## Engine operations and completion

| Operation | Native work | Evidence required before its domain receipt |
| --- | --- | --- |
| Inventory → hand | Resolve the exact selected list and call the existing `Actor_RemoveItem` virtual with that list and quantity. Retain only the engine-returned world reference. | Exact inventory count decrement, matching container-change event, actual returned reference/base/count, and matching/remapped existing UID when present. HIGGS then separately confirms physical grip. |
| Held → inventory | After HIGGS confirms release, call the existing `Actor_PickUpObject` virtual with the retained exact world reference. | World reference retirement, exact inventory count increase, matching container event and preserved/remapped existing UID in a fresh inventory list when present. |
| Consume held | For one ordinary non-poison potion/food or ingredient, pick up that exact reference and use `EquipManager::EquipItem` with the fresh matching UID list or plain homogeneous stack. | World reference retirement, the matching pickup and consumption-removal events, final inventory count and removal of the selected UID when present. This observes consumption of an instance; it does not independently measure the applied gameplay effect. |
| Equip/unequip game hand item | Use the live exact list and existing `EquipManager` wrappers. Map physical handedness into the engine equip slot, including bow/two-hand ownership. | Fresh exact worn-list state and actual equipped base form. The transaction owner additionally waits for a strictly newer coherent HIGGS drawn-equipment observation. |
| Compensate failed acquisition | Pick up the same retained dropped reference, or restore the prior hand equipment using a fresh exact list. | The corresponding actual inventory/equipment postfacts, followed by the transaction owner's independent equipment confirmation where applicable. |

The engine adapter keeps a private per-request instance lock in addition to transaction identity locks. Its native key includes the retained container, base form and persistent UID when present, so a relocated extra-list allocation cannot evade the lock through a new ticket. A duplicated UID in the live inventory is rejected as ambiguous; distinct valid UID stacks remain independent. Different tickets or consumers cannot mutate the same still-pending native source merely because their public identity tokens differ. A returned reference is never replaced with a newly spawned base form. The actual engine selection/removal call preserves extra data; existing UIDs are checked and changes are followed through copied `TESUniqueIDChangeEvent` records.

`BeginMutation` supplies exactly one permit in the existing executor callback. `Broker::InvokeTransfer` already fences that callback, including synchronous engine events and deferred world changes. The backend performs a final fresh resolve immediately before the engine call. Engine acceptance is not completion. When postfacts are deferred, the service stores the execution/permit and polls copied or freshly read facts at later main maintenance passes without issuing the mutation again. A missing or conflicting observation cannot become a committed receipt.

No mutation permit is issued for an unsupported or already stale source. After a permit has been issued, an exception, broken postcondition or failed compensation reports recovery-required facts rather than claiming rollback. Cancellation after a proven drop uses the normal one-shot compensation path. A lost receipt or a timeout after uncertain mutation cannot authorize a blind retry. Client unregistration stops future authority and public queries but does not retire an issued mutation's reference or private native lock: the pump asks the internal transaction owner whether an active/recovery pin remains, independently of client liveness. World resets invalidate future authority and release private engine pins only at the main pump; the coordinator retains its uncertain historical facts.

## Finite capabilities and limits

The native engine is installed after the first main maintenance pass has connected the process-wide engine event sources. Before that, capabilities are zero and selection/executor requests return NotReady. Consumers may retry readiness and query the table again. The portable production source closure advertises no native capabilities by itself.

The backend selects ordinary playable weapons, armor, ammunition, books, potions/food, ingredients, miscellaneous items, keys, soul gems and scrolls. Inventory transfer is not scripted activation. Containers, moveable statics, proxy/display spawning, arbitrary other inventories and custom activation semantics remain external or unsupported. Torches are not advertised by this finite backend. Consumption excludes books, poison, quantities other than one, and custom-data instances without a persistent UID. Such rejection precedes pickup or a permit.

Hand equipment covers weapons, shields and scrolls. A two-handed weapon/bow requires both physical hands reserved and its correct physical equipment hand. Body armor needs a separate worn-biped observer; it cannot be confirmed through a hand's equipped-form field and is explicitly unsupported here. This service does not supply that missing body-equipment contract.

Pending operations retain exact references through observations and compensation. A bounded ring holds 128 copied container events and 128 copied UID-change events. If too much intervening activity loses the required observation window, the backend fails closed. The service holds at most 128 selections, 64 consumer executor registrations and 128 pending native operations; release completed selections rather than treating them as a permanent item database. Recovery-required transactions deliberately keep their item locks and pins until their uncertainty is resolved or the world epoch ends.

## Existing bindings and CommonLib preparation

No new executable address is introduced. The native adapter uses HIGGS's existing `Actor_RemoveItem` virtual 0x56 (the upstream source documents actor implementation RVA 0x607F60), existing `Actor_PickUpObject` virtual 0xCE, and the public SKSE VR `EquipManager` wrappers (EquipItem 0x640A90; UnequipItem 0x6411A0), existing reference-handle lookup, extra-list count and event-dispatcher wrappers. These declarations are compiled against the real external SKSE headers; offline compilation does not validate runtime opcodes or game semantics.

CommonLib can later provide the same typed engine calls, safe inventory enumeration, retained-reference/handle ownership, exact extra-data/UID access and container/equipment event subscriptions. HIGGS should retain transaction authority, native selection ownership, postfact receipts and physical-hand coordination. This stage does not modify CommonLib. A future richer body-equipment observer and a generic container-transfer contract remain separate requirements.

## Verification

Run `python tests/run_inventory_tests.py --build-dir <external-directory>`. It compiles a C11 ABI consumer, the actual portable ticket/coordinator source and the actual native adapter source on explicit SDK doubles. It exercises an inventory/world/grip/inventory round trip, native item locks across independently selected tickets after UID-preserving list relocation, duplicate-UID refusal and distinct-UID independence, retention after client unregistration and recovery, no-event no-commit behavior, actual consume and hand-equipment wrappers, strictly newer equipment confirmation, safe compensation, failed compensation, retained reference protection against form-ID reuse, world invalidation and more than 256 released selection lifecycles. A deliberately removed event gate must be detected.

The existing `tests/run_hand_tests.py` also executes the actual `PublishNativeItems` erasure path for 300 new references sharing a recycled form ID and duplicate opaque UID metadata, verifies monotonic native identities and retains an item through a released hand's in-flight transaction. Its native inventory pump is an explicit no-op seam; the inventory-specific fixture above executes the real inventory adapter. Full native DLL compilation is separate evidence. None of these fixtures is a running-game test.
